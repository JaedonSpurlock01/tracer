# Fail a stalled database request within its timeout

Every Tracer page is rendered on the server from PostgreSQL on each request: the app shell resolves the actor and the Organization, and the page runs its loaders, all through one request-scoped pool that reaches Neon through Hyperdrive over a Cloudflare socket. Nothing is cached between requests, so a page cannot render without the database. What the architecture can promise is that a request never waits longer than its timeouts, that a timeout is visible to the user and in the logs, and that stuck connections never pile up behind a hung page.

Until 2026-10-25 it promised that on paper only. The pool set a 10-second connect timeout and a 30-second query timeout, and a contract test proved both against a Node `net` server that never answered. Workers Logs showed 22 page requests in 7 days that ran from 30 seconds to the 100-minute invocation cap with under 100 ms of CPU and no PostgreSQL query, and in that week no request ever logged a timeout. pg reports a connect timeout by destroying the socket and waiting for the socket's `close` event; pg-cloudflare, the adapter pg uses inside a Worker, emits `close` only after the Cloudflare socket's `close()` promise resolves, and a socket that Hyperdrive never answers never resolves it. The timer fired, nothing happened, the browser gave up minutes later, and because the request's log line is written after the response, there was no line. The Node socket in the test emits `close` at once, which is why the test stayed green. Each reload opened another hung invocation on the same path, which is why a browser that had hit one stall kept hitting them while a fresh browser, on a new connection, often did not.

The decision is that Tracer owns the socket pg drives inside the Worker. `data/request-socket.ts` connects through `cloudflare:sockets`, pumps bytes to pg, performs the STARTTLS upgrade, and on `end` or `destroy` cancels the reader, aborts the writer, starts the close in the background, and tells pg on the next microtask. pg's connect timeout, pg-pool's connect timeout, and the request's pool close all finish on their own timers, and the read loop ends cleanly instead of rejecting after the pool closed, which pg-cloudflare had logged as an unhandled rejection on every request. The connect function is injected, so the contract test hands the pool a Cloudflare socket that never answers and asserts the query fails within the connect timeout; a Node socket is no longer evidence for the Worker path.

A timeout is also something the page says. `withRequestRuntime` wraps a pool timeout anywhere in the cause chain in a `DatabaseUnavailableError` whose digest is the constant `DATABASE_UNAVAILABLE`. Next.js keeps a server error's digest when it scrubs the message for the browser, so the error boundaries at `app/error.tsx` and `app/(app)/error.tsx` render the shared failure page, "The database did not answer", with Retry, and the `tracer.request` line carries the error name. Any other error keeps the generic failure page.

The consequence is a different failure mode, not fewer stalls. A stall that reached Hyperdrive and went unanswered now costs 10 seconds and one line in Workers Logs that names it, and the next stall is diagnosable from that line instead of from the absence of one. If Production keeps logging them, the lever is the Hyperdrive and Neon path, which the logs can now measure; the database driver is not it.
