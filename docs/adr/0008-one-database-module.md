# One Database module is the only way application code reaches PostgreSQL

Until 2026-10-25 three different pools reached PostgreSQL for the same repositories: the Worker request pool (six connections, timeouts, the request socket of ADR 0007, stats gathered by patching pg-pool), the Trigger.dev task pool (one connection, no timeouts, a Node socket), and the integration test pool (bare, tolerating server shutdown). Fifty-five modules took a raw pg `Pool`, nine of them carried their own copy of a transaction helper, and the Organization advisory lock was a separate call a transaction had to remember. Each pool bug this week, the one-connection deadlock recorded in ADR 0006 and the swallowed timeout recorded in ADR 0007, was found in Production because the test adapter was not the Production adapter.

The decision is one module, `data/database.ts`, with one interface: `query` runs a statement, `transaction` runs a callback inside begin and commit on a handle that can only query, taking the named advisory lock first when asked, `stats` reports the queries, waves, slowest statement, failures, and timeouts the owner paid, and `close` ends the pool in the background with a deadline. The 10-second connect and 30-second query timeouts live inside it, inside the Worker it drives the request socket, elsewhere pg's Node socket, and a timeout fails as `DatabaseUnavailableError`, the error the failure page names. The Worker request runtime, every Trigger.dev task run, and every integration test open it the same way; only the connection count differs. There are no other options.

The move lands in slices so the application stays runnable. The module first replaces the three pools while repositories that still take a pool receive the module's own, so every query already runs under the Production timeouts and the Production socket in tests. Repositories then take the Database in area order, the deadlock-prone Workspace routing and Provider Credential modules first, and the pool handle, the nine helpers, and Drizzle outside the Better Auth adapter are deleted when the last repository moves. That happened on 2026-10-25. The script-side bootstrap, retention fixture, runtime role, and call smoke modules moved too, because thirty integration tests call them and keeping them on a raw pool would have meant a second pool in each; the scripts open a Database the way a task does, and query-only modules take `Queryable`, which a script's own pg client still satisfies. `pool` is not on the `Database` interface; only `openDatabase`'s own result exposes it, for the module's contract and integration tests.

The consequence is locality. A stall rule, a lock rule, or a counting rule changes in one place and every page, task, and test sees it; a transaction cannot ask the pool for a second connection because its handle has no such method. The interface is the test surface: the contract tests hand the module sockets that never answer, and the integration tests run its transactions and shutdown tolerance against a real PostgreSQL. The cost is that repositories no longer hold a pg `Pool` and cannot reach for pg features the interface does not offer; that is the point.
